# channel 的发送与接收

让任务把结果交给接收者，理解等待、缓冲和结束通知。

## 任务已经会启动，结果怎样交回来

[goroutine](#/learn/go/go-goroutines) 可以独立计算，WaitGroup能等完成，Mutex能保护共享变量。另一种沟通方法是channel，中文常叫通道：一个有指定元素类型的值传递入口。发送者交入值，接收者取值。

**channel传递值；它不是HTTP连接，也不是自动启动任务的命令。**`make(chan int)` 创建整数通道。没有缓冲时，发送和接收需要配对，未配对的一方会等待。

## 完整例子：一方算，一方收

在独立Go练习目录替换main.go：

```go
package main

import "fmt"

func main() {
	results := make(chan int) // 只能传int，默认没有可暂存结果的缓冲空间。
	go func() {
		results <- 2 + 3 // 发送：等接收者配合，交出计算出的5。
	}()
	value := <-results // 接收：结果未到就等，收到后main才继续。
	fmt.Println(value)
}
```

```sh
go run .
```

输出：

```output
5
```

`chan int`是通道类型，`make`创建它。箭头 `<-` 的位置表明方向：`results <- 5`向右边的值取来发到results；`<-results`从results取值。它不是小于比较符，也不将整数转类型。匿名函数最后的括号是调用；前面的go使其在另一goroutine执行。

main接到结果才打印，所以不用猜Sleep时长。这个程序只有一次结果交换，发送结束后工作就完成；更复杂工作仍需明确等待剩余任务。

## 为什么放同一 goroutine 会卡住

如果删去go和函数包装，在main先写 `results <- 5`，再写接收，无缓冲发送会等接收者，但main停在发送处，永远走不到接收。在此纯演示中可看到deadlock错误。**阻塞是等待条件，死锁是所有必要条件都再也无法推进。**

缓冲通道 `make(chan int, 1)` 能先存一个值，因此同一goroutine可以先发一个再收。容量1不是永远不等：未取走就发第二个仍会阻塞。

## close 不是什么都终止

`close(ch)`表达发送方不会再发送。已缓冲的值仍可接收，取完后接收得到零值与false。这个片段用于已经创建的results，放在发送全部结束之后：

```go
close(results)
value, ok := <-results // 若已空且关闭，int零值为0，ok为false。
```

不要只凭读到0判断结束，因为0也可能是合法结果；要用ok。对关闭通道再发送会panic，重复关闭也会panic。多个发送者应由知道“所有发送已结束”的负责方关闭；接收者不能随便关仍有人要发送的通道。

**关闭结果通道并不自动取消所有goroutine。** 停止工作需要下一节context或自己约定的信号；消费者提前放弃时，还应防止生产者永远阻塞发送。

## 预测再实验

保持默认无缓冲版本，改计算为3*4应输出12。再创建容量1的通道，改为main中先发送12再接收；预测能够完成。随后临时增加第二次发送而不接收，观察阻塞/死锁，停止并还原。

### 参考答案

缓冲提供暂存空间，不提供无限队列。等待关系决定能否继续，不能用“有channel所以安全”代替设计。

## 独立变式

启动一个生产者发送三项整数后关闭通道，main用带ok的接收循环累加，结果应为预先写出的总和。若改用range遍历通道，应解释它何时结束，并验证漏close会等不到结束。
